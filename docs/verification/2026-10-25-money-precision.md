# 金额精度检查与修复

## 当前金额设计

| 链路 | 实现与结论 |
| --- | --- |
| 前端输入 | 元以字符串解析，BigInt 拼接整数分，拒绝超过两位小数及超出 Number.MAX_SAFE_INTEGER 的金额，不使用浮点乘法或静默四舍五入 |
| 后端校验 | OrderValues 拒绝 Double / Float，使用 BigDecimal.longValueExact() 验证非负整数分，领域模型保存 Long |
| 数据库 | 总额、单价、会员价均为带非负约束的 BIGINT 分 |
| 查询统计 | PostgreSQL 对整数分精确求和，金额合计转为十进制字符串返回；前端 BigInt 格式化 |
| Excel | 金额通过 BigDecimal 转成元字符串后写入单元格，避免 Excel 浮点数的有效位限制；图片尺寸等 double 运算不参与金额 |
| 业务口径 | 整单约定金额仍由员工填写，不自动按商品单价和数量重算；付款状态与金额相互独立 |

整数分方案本身适合当前两位小数金额，无需将数据库和领域模型整体改为小数类型。

## 发现与修复

前端通用金额显示、客户填单核对草稿回填及历史核对结果展示使用了除以 100 后 toFixed(2) 的浮点路径。
例如 9007199254740990 分原先会变成 90071992547409.91 元，准确值应为 90071992547409.90 元。草稿回填错误还可能在再次保存时改变金额。

上述路径及已有汇总格式化现在共用 money.ts 的 BigInt 精确转换。
接口读取同时检查数字金额是否处于 JavaScript 安全整数范围，超出时显示核对错误，阻止失真金额进入详情和编辑草稿；字符串汇总不受此限制。
识别、表单输入、数据库及导出原有精确路径保持。

## 已确认并统一的金额范围

订单总额、商品单价和会员价的前后端上限统一为 9007199254740991 分，即 90071992547409.91 元；继续使用整数分数字接口。
后端 OrderValues.money 统一检查该上限，覆盖正式订单创建、编辑、追加商品及客户填单核对，识别金额也引用同一常量。超限返回 400 VALIDATION_FAILED，不截断或四舍五入。
非金额的版本等整数不受此限制；跨订单汇总继续使用精确字符串，可以超过单笔上限。
本地现有正式订单、商品价格和客户填单核对金额的只读检查均发现 0 条超限记录；不回写、截断或删除历史数据，不增加数据库迁移。
统一上限后的 OrderValuesTest、OrderTest、OrderRecognitionTest、ArchUnit，以及正式订单写入/汇总、客户填单核对的 3 项 HTTP 集成用例均通过；验证边界值接受、超限拒绝且版本/审计不变、汇总可超过单笔上限。
