# 套餐图片保存阻塞与认证接口超时

排查时间：2026-11-15 20:18—20:25（Asia/Shanghai）。线上版本：`20261114T152444Z-access-recovery-022e59f`。

后续代码修复及验收见 [图片处理隔离与套餐恢复验证](2026-11-15-image-resilience.md)。本文件记录首次故障现场与重启恢复，不代表后续修复已经发布。

## 结论与证据

套餐创建请求阻塞在 JPEG 解码/缩图路径，期间整个 Java 应用响应严重停滞。公网静态页面正常，但 `/api/auth/csrf` 在 15 秒内没有返回数据，应用容器为 `unhealthy`。前端初始认证请求没有超时保护，因而持续显示“正在读取最新数据”。

- PostgreSQL 事务开始时间为北京时间 19:56:57，持续处于 `idle in transaction / ClientRead`；最后一条查询为套餐图片查询。数据库在等待应用继续执行，未发现该事务等待数据库锁。
- 线程快照中的 `http-nio-8080-exec-1` 停在 `JPEGImageReader.readImage → Thumbnailator → JavaOrderImageValidator.encode:67 → validate:41 → OrderPackageService.writeImages:96 → create:66`。
- 应用 CPU 为 102.21%，容器内存约 451.5 MiB / 640 MiB；宿主机可用内存约 636 MiB、磁盘可用 23 GiB。PostgreSQL 和 Redis 健康，容器没有 OOM kill 或重启记录。
- Hikari 在 19:59、20:03、20:11 报线程饥饿；线程快照显示多条请求停在对象分配处，VM Thread 累计 CPU 约 1540 秒，支持 JVM 内存回收/运行时停滞的判断，但没有 GC 日志或原图复现，不能断言已证明具体 GC 或解码器缺陷。
- JVM 堆上限 256 MiB；图片允许最高 2400 万像素。当前图片校验先全量解码，再由 Thumbnailator 重新解码和缩图，存在较高内存峰值的风险。未取得本次原图尺寸，不能将该风险直接当作已证实的最终根因。

## 恢复与数据核对

保存应用日志和线程快照后，仅重启 `app`，未修改代码、部署配置或数据库记录。未提交事务随应用连接关闭而回滚。

重启后应用健康检查为 `UP`；公网 CSRF 接口恢复 200，首次验证约 0.6 秒。独立匿名会话的 CSRF 与 refresh 流程合计约 0.2 秒，refresh 正常返回 401 `AUTHENTICATION_FAILED`。该检查证明认证链路能正常返回，不代表已使用员工账号完成实际登录。

数据库现有套餐共 3 条，今晚 19:30 以后创建的套餐为 0；未提交空闲事务恢复为 0。本次新套餐没有保存成功。

## 后续修复方向

获取触发故障的原始 JPEG，在相同 JDK、256 MiB 堆限制下隔离复现，记录图片尺寸、GC 与解码耗时。随后针对证据调整图片解码内存峰值和并发限制，并为初始认证请求补充超时退出。修复前避免重复提交同一原图，可先保存无图片套餐。
