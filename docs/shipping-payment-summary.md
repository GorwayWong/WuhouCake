# 周历出货付款汇总与制作视图

周历选中日期后，独立的 `DayShippingSummary` 组件显示该日有效出货订单总数、待配送数，以及已付款和未付款两组的订单数、订单总金额。下方订单状态和付款状态筛选只改变列表，汇总不会随筛选变化。

## 统计口径

- 使用 `requested_receive_date` 与所选日期匹配，包含自提和配送订单、包含已完成订单，排除 `CANCELLED`。
- 付款分组依据订单当前 `PAID` 或 `UNPAID` 状态，金额使用 `total_amount_cents`，每张订单只计算一次，不按商品数量或商品单价累加。
- 待配送数量使用 `WAITING_DELIVERY` 状态；制作中和配送中的订单仍在总数中，但不计入待配送数量。
- 未报价订单计入订单数，金额合计只包含已填写金额，并返回缺失金额订单数。整组均未填写金额时显示“待补金额”；真实零元与无订单显示 `¥0.00`。
- 日期是出货归属日，金额不是所选自然日的实际收款流水。
- `paidWithoutDateOrderCount` 统计同一出货范围中当前已付款但 paid_at 为空的订单数，作为历史付款日期缺失提醒；不改变原有付款分组、金额和收款日期筛选。

界面分别使用“按出货日”和“按付款时间”标签。出货汇总强调当前付款状态、包含提前付款；“当日付款订单”依据人工记录的付款日期，出货日期不限，非支付流水。当日付款订单为零时说明是零条可归日记录，不能据此判断出货订单没有收款。缺少付款日期的已付款出货订单显示“付款日期待核对”，不推算日期或自动回填。

## 后端契约

`GET /api/orders/workbench/payment-summary?date=YYYY-MM-DD` 要求 `ORDER_READ` 与 `ORDER_AMOUNT_READ`，未登录返回 401，缺少权限返回 403。日期必填且必须有效。该接口不使用订单状态、付款状态等列表筛选参数。

响应 `data`：

```json
{
  "date": "2026-10-23",
  "totalOrderCount": 4,
  "waitingDeliveryOrderCount": 1,
  "paid": {"orderCount": 2, "amountCents": "19134", "missingAmountOrderCount": 0},
  "unpaid": {"orderCount": 2, "amountCents": "0", "missingAmountOrderCount": 1},
  "paidWithoutDateOrderCount": 0
}
```

金额为分单位的十进制整数字符串，数据库使用数值聚合并转字符串；前端通过 `BigInt` 格式化，避免汇总金额超过 JavaScript 安全整数范围后失真。查询在订单主表上完成，不加载明细、不关联商品表，无数据迁移或业务写入。

## 前端更新规则

三个付款明细入口均打开独立列表页：当天付款订单、当天出货已付款订单、当天出货未付款订单。列表每页 10 条，显示订单号、下单时间（需要业务资料读取权限）、出货日期、付款时间、整单金额及当前付款和订单状态。左上角逐级返回列表、原工作台，保留日期、视图、筛选、页码和滚动位置；业务数据继续刷新。

`GET /api/orders/workbench/payment-orders?date=YYYY-MM-DD&kind=RECEIPT&page=1` 要求 `ORDER_READ` 与 `ORDER_AMOUNT_READ`。kind 为 `RECEIPT`、`SHIPPING_PAID` 或 `SHIPPING_UNPAID`；page 从 1 开始，返回 date、kind、实际 page、total 和 orders。请求页超过末页时返回末页。

RECEIPT 使用北京时间当天的左闭右开付款时间范围，当前仍为已付款，出货日期不限，包含已取消订单；付款时间缺失不计入。SHIPPING 两组与出货汇总完全一致，排除取消订单。前者按付款时间倒序、订单号排序，后者按交接时间（空值在后）、订单号排序。金额为分单位字符串，缺失为 null。订单改为已付款时记录服务器时间，重复标记不更新时间；改回未付款清空，再次付款重新记录。

员工业绩中的“已付款订单总额”“未付款订单总额”按整单当前状态汇总约定总金额，不按单个商品拆分付款。

查询缓存键为 `['workbench', 'payment-summary', date]`，不含列表筛选值。切换日期时独立加载，不将上一日汇总冒充新日期数据。付款状态、金额、出货日期、取消状态变化，以及 SSE 重连或恢复在线时，沿用现有工作台缓存失效机制刷新。

加载、无订单、金额缺失及刷新失败均有独立提示。刷新失败但存在同日缓存时标注旧数据；无权限时不显示缓存金额。制作岗位不发送付款汇总请求，全日订单数和待配送数从未筛选的当日列表排除取消订单后计算。

## 制作视图

周历蛋糕胚统计沿用 `cake-bases` 的尺寸、蛋糕胚口味、商品数量分组，前端按尺寸显示数量小计及口味明细。以所选出货日为准，排除取消订单、已移除商品和非蛋糕商品，包含已完成订单，不受下方筛选影响。口味读取 base / 历史 cakeBase，缺失沿用原味；奶油 flavor 不参与分组。小数尺寸保留，缺失尺寸单独列出。

`PASTRY_CHEF` 在员工管理中显示为“糕点师／裱花师”。详情和工作台使用有效权限判断展示，不按岗位名称硬编码。纯制作岗位不展示付款筛选、金额、客户资料、会员信息、地址、下单时间、下单员工归属、财务查询和导出入口；兼任前台或经理时按权限并集恢复可见资料。

工作台卡片突出款式缩略图、计划出品时间及制作参数，按计划出品时间分组。订单详情先展示计划出品时间、特殊要求和备注，再展示可点击放大的款式图片；蛋糕胚口味、尺寸、奶油、夹心、祝福语和特殊要求逐行对齐，缺失要求显示“无”。`flavor` 沿用现有“奶油”含义，`base` / `cakeBase` 表示蛋糕胚口味，不新增重复字段。工作备注默认折叠，制作与图片操作继续使用现有流程。

服务端裁剪结构化客户、金额和下单资料。备注、商品要求和参考图片为制作内容，不做自动内容识别或脱敏；完整活动日志仍要求敏感数据读取权限，制作岗位通过只读 `NOTE` 的接口查看工作备注。

## 验证

- 后端单元及 HTTP 切片测试：独立聚合、精确金额、日期校验、权限隔离、备注类型固定、创建时间裁剪、兼岗权限并集。
- PostgreSQL / Redis / HTTP 集成测试：多商品单不重复计数、完成及取消订单、零元与缺额、跨日、大额汇总、付款变化、制作岗读取与操作、已有令牌下兼岗权限变化。
- 前端测试：权限展示、制作字段语义、列表筛选隔离、金额格式、汇总缓存按日期隔离、付款及迁日通知刷新。
- 浏览器检查：使用合成接口数据分别验证前台和制作账号的桌面与手机视图、筛选后汇总不变、无敏感资料显示、图片放大和无横向溢出；真实数据库行为由上述集成测试验证。
