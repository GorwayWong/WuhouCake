# 客户扫码填单

## 业务流程

前台或管理人员在工作台「客户填单」中生成自己的固定二维码。客户免登录填写联系电话、配送／自提、取货日期和具体时刻、地址以及一个或多个商品，会员手机号选填。客户提交后只能联系发码客服更正，本期没有公开历史查询、详情查询或修改接口。

提交超过 30 秒或没有收到有效回执时，页面显示结果待确认。向客服核对后，可手动重试，刷新页面或重试时遇到限流仍沿用原请求。首次提交收到明确的填写校验拒绝后，页面保留输入供修正。入口停用或重置后，请联系发码客服核对。同一入口重新启用后，可点「重试」重新读取入口，再手动重试提交。收到有效填单回执或确认放弃重试后清除暂存，收到编号后可选择「再填一单」。

重新检查入口时，单次读取最多等待 30 秒。读取失败会显示本次的错误原因，已暂存的填单可以在入口恢复后继续重试。

填单独立于正式订单，状态为 `PENDING`、`CONFIRMED`、`DELETED`。待确认填单不进入制作日历、经营统计、员工业绩或订单导出。前台和管理人员默认查看全部客服的待确认填单，可切换为自己二维码收到的填单；只有糕点师岗位的员工不能处理这些填单。

员工核对时可保存草稿。确认前必须补齐整单约定总额和在职业绩归属员工。核对页只填写取货和出品：取货是客户或配送员从门店取走商品的时间，配送订单不表示送达。出品默认提前一小时，可手动调整或恢复自动。核对页的报价只填写整单约定总额，整单金额不按单价自动求和。能匹配到原商品的历史单价与会员单价在核对页隐藏，保存核对及转为正式订单时保留。新增商品的逐项报价为空。确认生成正式 `CAKE_BASE`／`UNPAID` 订单，之后沿用员工既有修改与履约规则。

日期通过日历选择，小时与分钟分别下拉选择，支持 00–23 时和 00–59 分。客户扫码及核对要求完整取货时间；员工新建、改期允许只填日期，具体时刻待定，不补零点。改日期会清空旧时刻；自动出品随取货变化，手动出品保留。

公开字段名保持兼容：客户内容 `requestedReceiveAt` 表示取货时间；员工核对提交同时赋值到 `plannedHandoffAt`。正式订单优先使用 `fulfillment.plannedHandoffAt`，历史缺失时回退 `requestedReceiveAt` 和 `requestedReceiveDate`。新建及明确改取货时同步旧字段；历史不批量回填，原值不同在核对区展示。`origin.requestedReceiveAt` 和原始客户提交仅为溯源快照。日历按有效取货日期归日，普通时间轴按取货、制作时间轴按出品分组。


V13 迁移只对已确认的客户来源订单回填核对后的期望时间，且要求其北京时间日期与正式订单当前日期一致。历史人工录单、日期已更正不一致或缺少核对时间的订单继续保留未知时刻，不推算或覆盖当前日期；未知时刻不阻止其他资料更正。

| 信息 | 保存含义 |
| --- | --- |
| 客户填写来源 | `CUSTOMER_SUBMITTED`；手机号未经验证，不能视为客户身份 |
| 发码客服 | 原始二维码所属员工及姓名快照，不自动获得业绩归属 |
| 确认员工 | 正式订单的 `createdBy` 及创建活动操作者 |
| 业绩归属员工 | 员工确认时显式选择，沿用现有统计字段 |
| 客户提交时间 | 保存在原始填单中 |
| 订单创建、确认时间 | 取客服确认时刻 |

扫码未提交草稿保存在当前浏览器，按二维码入口隔离。填表内容最后一次修改起 24 小时内可重扫同一有效二维码恢复。发送前先尝试将原请求正文和幂等键写入 IndexedDB，浏览器仍可访问本机存储时，待确认记录保留到取得回执或确认放弃。使用共享设备时，请在离开前核对并处理待确认记录。页面已知有草稿而写入失败时，会提示本次未发送，并保留当前输入。页面没有读到或写入草稿时，仍可在当前页提交和重试。此时可能只有当前标签页的会话记录或页面内存可用，请保留当前页面。

发送前若发现会话存储中有旧的待确认提交，本次填写会留在页面中，页面暂停发送新请求。可先复制需要保留的输入，再选择「恢复原提交」，使用原来的内容核对结果。放弃旧提交的重试记录后，页面会提示恢复另一份仍在本机的草稿。

客服核对输入按员工账号和填单隔离保存。刷新或同账号重新登录后可恢复。版本冲突时，先核对同事改动，互不重叠的字段可一并保留，同一字段或商品须确认采用哪个版本。历史商品 ID 缺失或无法安全对应报价时，采用最新商品列表继续核对，本地内容可复制。填单被他人确认或删除后，仍具备读取权限的原编辑人可查看自己的本机草稿。放弃草稿时按当前页面持有的版本清理。另一标签页已经写入新版时，页面会提示冲突并保留输入。

同联系电话、同北京时间取货日期的记录提示疑似重复，覆盖所有客服的待确认填单及扫码、手工创建的正式订单，不限制新旧顺序。待确认填单优先使用已保存核对内容，否则使用原始填写；正式订单使用当前资料。电话比较去除空格、括号和短横线，不推断国家区号。已确认填单只展示对应正式订单；已删除填单不参与，取消订单仅作历史参考，完成订单仍须核对。商品、数量、金额和具体时刻供人工比较，不作为排除条件。

扫码确认和手工录单按联系电话、北京时间取货日共用事务锁。扫码确认持锁后重新核对候选，候选变化时返回 `DUPLICATE_REVIEW_REQUIRED`。手工录单匹配到未取消的有效正式订单时，在保存按钮旁提醒有权限查看订单及电话的员工核对。若属于两笔独立订单，点「按独立订单保存」即可继续。无匹配时照常保存。

确认页展示全部匹配记录及详情入口。有待确认填单或未取消正式订单时，客服须勾选「已核实，这是独立订单，继续接单。」。候选新增、修改、确认或删除后，旧勾选失效，须重新核对。人工放行的确认日志保存匹配记录快照及独立订单决定，操作者与时间沿用活动字段。检测基于查询时已提交的数据，不提供跨录单入口的强唯一约束。

客服删除待确认填单后，日常列表不再展示，原始内容和删除活动继续保留用于追溯；没有恢复入口。确认后的填单不能通过此删除功能删除正式订单，不自动覆盖、合并或删除其他记录。

客户填单导航展示全部待处理数量，每 30 秒刷新。前台列表每 15 秒刷新，也可手动刷新；保存核对、确认及删除后同步刷新。二维码无需每天重建，保持启用及所属员工有效时可持续使用，重置后旧链接失效。客户端本期只填单，不提供支付和订单状态查询。

## 字段契约

员工核对表单将商品类型放在商品标题旁，蛋糕按“名称 → 规格（寸）/数量 → 蛋糕胚/夹馅 → 奶油 → 祝福语 → 特殊要求”排列；360px 及以上保留成对字段两列，窄屏改为单列。界面“规格（寸）”对应 size，“蛋糕胚”对应 base，字段名与尺寸必填规则保持。

客户填单页默认添加蛋糕，蛋糕名称默认为“蛋糕”。顾客可将单项切换为“其他”，填写商品名称、商品说明、数量及其他要求。支持添加和移除多项商品。尺寸（寸）/数量、内胚/奶油分别成对排列，之后为夹心馅料、祝福语、其他要求。尺寸仍必填；夹心馅料提示默认芒果，可换火龙果、草莓、奥利奥碎、黄油脆片、脆啵啵、马蹄爆爆珠，最多混搭三种（文字说明，由客服核对）。每项商品末尾都可添加参考图片，恢复草稿时恢复已上传的图片。提交按钮前完整展示客户提供的“订购需知”：付款为准、各距离运费条件、夹层替换与三种混搭、蜡烛火柴刀帽标配、各尺寸叉碟份数及超出标配另购说明。须知仅展示，不参与支付或运费计算。

客户页面奶油空白时明确提交 `原味动物奶油`，客户明确填写的奶油保留。员工核对、历史记录及直接 API 请求未填奶油时，继续沿用现有 `原味奶油` 默认值；不批量更改历史数据。

蛋糕使用现有规格字段：必填的 `size` 支持自由文本，最多 2000 字符，保存时去掉首尾空白；`base` 为内胚，默认原味；`filling` 为夹心／配料，默认芒果；`flavor` 为奶油，默认原味奶油；`message` 为祝福语；`requirements` 为其他要求。界面品类为蛋糕 `CAKE` 和其他 `OTHER`，旧细分类名称仍可兼容读取。非蛋糕使用名称、数量、specification（规格）、requirements（其他要求）简表，不自动补入蛋糕的内胚／夹馅／奶油默认值，也不强制蛋糕尺寸。每份填单 1–30 项商品，名称最多 128 字符，手机号最多 32 字符，地址及每项规格最多 2000 字符。手机号只校验填写格式和长度，不验证持有人。

客户表单中不存在价格、业绩归属、员工身份、来源和订单状态。公开请求使用独立 DTO，未知字段拒绝；属性也仅接收上述客户字段。电话号码接受 6–15 位数字，可带国际前缀 `+`、空格、括号或短横线；保存前移除分隔符，不推定国家区号，不验证持有人。联系电话与会员手机号分别保存，不触发会员查询、定价或扣款。

客户原始填写不可覆盖。核对记录包含更正前后值、真实操作员工及时间；正式订单创建日志标记「来源：用户填写」，订单详情提供原始填写与处理记录入口。客户字段快照与差异方法集中在 `CustomerSubmission` 中，用作未来修改能力的基础；本期没有客户修改用例或开关，未来须另行确定身份验证与修改状态规则。

## HTTP 接口

客户填单二维码在浏览器本地生成带完整午逅 logo 的 PNG，预览和下载使用同一图片。输出为 640 像素、H 纠错等级，四模块白边，中心 logo 含白底区域不超过边长的 20%。员工切换及链接重置后重新生成；图片加载或合成失败时显示重试入口，不提供不完整图片下载。

JSON 响应沿用 `ApiResponse`。公开入口支持以下操作：

| 方法和路径 | 行为 |
| --- | --- |
| `GET /api/public/order-entries/{token}` | 返回有效入口的客服显示名 |
| `POST /api/public/order-entries/{token}/items/{itemId}/images/{imageId}` | 用 multipart 字段 `file` 暂存当前商品图片。重复上传使用原图片 UUID |
| `GET /api/public/order-entries/{token}/items/{itemId}/images/{imageId}` | 预览该入口下尚未提交的图片，须同时持有商品和图片 UUID |
| `POST /api/public/order-entries/{token}/images/status` | 只读批量检查。JSON 数组最多 40 组 `{itemId, imageId}`，返回该入口下暂存缺失的图片 UUID 数组。单独统计公开 JSON 频率限额 |
| `POST /api/public/order-entries/{token}/submissions` | 提交填单，必带 UUID `Idempotency-Key`；只返回填单 ID 和编号 |

公开请求正文为 `phone`、`memberPhone`、`fulfillmentType`、`address`、`requestedReceiveAt`、`items`。每项商品包含 `name`、`productType`、`quantity`、`attributes`。有图片的填单为每项商品附带稳定 `itemId`，通过 `imageIds` 指定该商品的图片。时间用带偏移 ISO 8601，界面按北京时间显示；`requestedReceiveAt` 同时确定取货日期。

员工端接口均需有效员工登录，服务端再次检查岗位：

| 方法和路径 | 行为 |
| --- | --- |
| `GET /api/customer-submissions?mine=true&status=PENDING&page=1&size=20&keyword=` | 分页查询；支持 `PENDING`、`CONFIRMED`、`ALL`，省略状态仍默认待确认；可选全部客服。关键词匹配原始／核对手机号的连续号码片段，或带／不带 F 的完整填单编号。工作台用 `view=summary` 获取 `submission` 和 `requiresAcknowledgement`；省略 `view` 返回原列表格式 |
| `GET /api/customer-submissions/pending-count` | 全部客服待处理总数，返回 `{count}`，不返回客户资料 |
| `GET /api/customer-submissions/{id}` | 原始内容、核对结果、疑似重复记录及核对 token、处理日志 |
| `GET /api/customer-submissions/{id}/items/{itemId}/images/{imageId}` | 核单岗位读取指定填单的商品图片 |
| `POST /api/customer-submissions/{id}/items/{itemId}/images/{imageId}` | 待确认填单的补图上传，沿用订单图片上传权限 |
| `PATCH /api/customer-submissions/{id}` | `{expectedVersion, review}` 保存核对结果 |
| `POST /api/customer-submissions/{id}/confirm` | `{expectedVersion, duplicateCheckToken?}` 确认生成正式订单；需核对时提交当前 token |
| `DELETE /api/customer-submissions/{id}` | `{expectedVersion}` 软删除未确认填单 |
| `GET /api/customer-submissions/entry?ownerId=...` | 本人二维码；管理人员可查询同事二维码 |
| `POST /api/customer-submissions/entry?ownerId=...` | `{action}`：`CREATE`、`ENABLE`、`DISABLE`、`RESET`；其他员工先由本人生成入口 |
| `GET /api/orders/{id}/customer-origin` | 登录员工读取正式订单来源、发码客服及客户原始期望时间；员工直接录单返回 null |

`review` 包含客户 `content`、`totalAmountCents`、`creditedEmployeeId`、`plannedHandoffAt`。旧客户端仍可传入与商品逐项对应的 `prices`，服务端校验列表结构并忽略新的报价值，按商品标识保留已有历史报价。金额单位为非负整数分，空与零不同。状态变化使用版本校验；`409 CONCURRENT_MODIFICATION` 后读取最新状态人工核对。保存与确认是两个独立操作，不自动覆盖他人核对结果。确认按钮旁列出尚未保存、缺少总额或归属员工等条件；品类、数量、蛋糕尺寸及确认必填项返回对应 SUBMISSION_* 错误码和具体中文提示。

员工核对商品使用 UUID `itemId`。修改名称、数量、规格或顺序时继续提交原标识。历史报价由服务端按标识关联，新增商品报价为空。V29 为已核对的待处理填单补齐商品标识，保留原商品顺序及报价。旧请求未提交标识时，仅按唯一且完整的商品内容匹配。无法安全关联历史报价时返回 `409 SUBMISSION_ITEM_ID_CONFLICT`，页面保留输入并提供读取最新结果的入口。无图填单的幂等指纹沿用无商品标识的格式。有图填单的商品及图片标识参与指纹计算。

员工列表与详情 GET 在各自的只读可重复读事务中组装响应，保证单次响应的主记录、关联记录和计数使用同一数据库快照。列表先计数，再将页码限制到有效范围；返回的 `page` 为实际页，空队列返回第 1 页。前端跟随实际页并保留搜索、状态与归属条件，防止同事处理末页订单后显示错误空态。保存、确认和删除仍沿用原事务与版本校验。

详情和完整列表项的 `duplicates` 返回记录种类、ID、版本、状态、订单号、联系电话、当前取货日期和时刻、商品名称与数量、总金额、经办员工、创建时间及 `requiresAcknowledgement`。正式订单的 `fulfillmentType` 用于显示配送和自提状态。`duplicateCheckToken` 绑定当前填单 ID／版本和候选集合，展示字段不参与计算，填单非待确认时为 null。确认事务内重新查询并比对 token；旧 `acknowledgedNewerSubmissionId` 请求字段仍可解析，但不作为放行依据。

二维码 `CREATE` 创建启用入口，已有入口不受重复创建影响；`RESET` 仅轮换令牌，保留当前启停状态；只有 `ENABLE`／`DISABLE` 改变启停状态。实际创建、变更和重置通过审计模块 `appendChange()` 与二维码写入同一事务，审计失败整体回滚。审计动作是 `order.entry_created`、`order.entry_enabled`、`order.entry_disabled`、`order.entry_reset`，记录实际操作者、入口和所属员工、时间、服务端请求 ID、启停前后值及令牌是否轮换，不记录令牌或完整链接；无变化的幂等操作不新增变更日志。管理人员代操作时与所属员工分别记录。

管理接口分别返回启停开关 `enabled` 和归属员工的接单资格 `ownerEligible`。管理页在两项都满足时显示「接收填单中」并提供打开及下载二维码的入口。

公开 GET 使用只读事务和普通查询，不获取员工或入口行锁。POST 先共享锁定所属员工并核查在职、岗位，再共享锁定入口并复核令牌及状态；锁保持至填单事务结束。身份模块的共享校验方法要求调用方事务，二维码管理按相同的「所属员工 → 入口」顺序获取锁。多个提交可同时持有共享锁，而归档、岗位变更、停用和重置与提交互斥。已持锁的合法提交可先完成，之后管理变更生效；变更已提交后的新请求会被拒绝。

同一入口与幂等标识只接收同一份规范化内容，不同内容返回 `409 IDEMPOTENCY_KEY_CONFLICT`。新请求使用带版本的指纹，尺寸按保存的文本参与比对。V39 使用已核实的 V37 绝对分界时间校正历史指纹标记。旧格式请求继续兼容原样重试，包括 V26 的尺寸归一化。确认事务原子保存订单、填单状态、唯一关联与日志；重试已成功确认的操作返回原订单，不再建单。缺少必要的核对 token 或 token 已过期时返回 `409 DUPLICATE_REVIEW_REQUIRED`；前端刷新候选、取消勾选并保留未保存输入。

## 部署与保护

前后端保持同源，代理 `/api` 到后端并给前端提供 SPA 入口。`dev` 允许局域网 HTTP 源站；`prod` 必须使用 HTTPS，即使同时启用 `dev` 也不能放行 HTTP。其他环境仅对 localhost、127.0.0.1 和 ::1 放行 HTTP。客户页面路径为 `/#/fill/{token}`。二维码通过浏览器本地 `qrcode` 生成，不请求外部二维码网站。

| 环境变量 | 默认及用途 |
| --- | --- |
| `CUSTOMER_ENTRY_PUBLIC_ORIGIN` | dev 默认 `auto`：启动时读取 Wi-Fi 局域网 IPv4，使用 5173 端口；无可用 Wi-Fi 时回退本机并记录提示；显式 HTTP/HTTPS 源站覆盖自动探测。自动模式仅限 dev 且未启用 prod。前端用 `npm run dev -- --host 0.0.0.0 --port 5173 --strictPort` 启动前端；prod 使用配置的实际 HTTPS 服务器 IP 或域名源站，不能使用 auto，不能带路径、凭证或查询参数 |
| `CUSTOMER_ENTRY_PER_MINUTE` | 每来源 IP 每分钟 10 次提交 |
| `CUSTOMER_ENTRY_PER_HOUR` | 每来源 IP 每小时 100 次提交 |
| `CUSTOMER_ENTRY_MAX_BODY_BYTES` | 131072，即 128 KiB；硬上限 1 MiB |
| `CUSTOMER_ENTRY_TRUSTED_PROXIES` | 默认空；逗号分隔的可信代理准确 IP 地址，不接收网段表达式 |

Redis 使用既有身份配置的命名空间，原子维护分钟和小时固定窗口计数。它限制提交请求，不按手机号封禁客户；超限返回 `429 SUBMISSION_THROTTLED`，Redis 故障返回可重试的 `503 SERVICE_UNAVAILABLE`。入口可由本人停用或重置，离职归档及不再具有前台／管理岗位时停止接收新填单；已有内容继续由其他员工处理。

默认忽略所有转发头。仅当直连来源在可信代理清单内，才从 `X-Forwarded-For` 右侧向左取第一个不受信任的来源。代理必须正确追加真实来源；勿同时开启会预先改写 `remoteAddr` 的全局转发头处理，以免绕过本入口的可信边界。对外代理同步限制请求大小，并避免把填单正文、手机号和二维码 URL 记录到访问日志。

发布前须配置实际源站，并在实际 HTTPS、代理及手机上验证二维码、填单和员工处理流程。本地或浏览器手机视口通过不等于已上线。

蛋糕内胚、夹馅和奶油缺失、为 null、空字符串或纯空白时，分别使用原味、芒果和原味奶油，客户明确填写的值保留。客户填单与员工核对表单在字段标题旁显示“不填默认…”小字。历史记录读取时补齐默认值，不执行批量改库，以后保存时写入。

顾客和客服可为每件商品选用最多 5 张 JPG/PNG，每张上传文件不超过 5 MiB。每次提交和核单保存合计最多 40 张、处理后共 32 MiB。顾客选图后，原文件与文字一起保存在当前浏览器草稿中，按同一有效期保留。点击提交预订后按顺序上传图片，全部就绪后才发送填单。上传中断时可恢复原草稿，再点提交继续。旧草稿暂存仍有效的图片沿用原 ID，失效时才从本机副本补传。顾客提交的原图保存在原始填单中。客服可排除和恢复顾客图、补传照片，核定结果随填单版本保存。确认接单时，核定图片与正式订单同时写入。未关联的暂存图片和从核定结果移除的客服补图在 48 小时后清理。原提交尚未写入且图片已失效时，重试返回明确的图片错误，先批量确认缺少的图片，再用本机原文件按原图片标识补传缺图并重试同一份请求。补传中断后仍从服务端实际缺少的图片继续。无本机副本且图片无法恢复时，页面标出失效图片，顾客可移除或重新选择。每个入口只保留一份可编辑草稿。带本机附件的新版草稿按原有效期保留，旧页面需刷新后才能读取或编辑。旧会话的待确认请求单独保留原正文和幂等键。提交因图片失效或总量超限被拒绝后，只有草稿槽位为空或对应同一请求时，才将原填写内容恢复为草稿。已有记录暂时无法写入时，请保留页面，待存储恢复后点「恢复编辑」。补传后若再次收到缺图答复，页面会重新查询，并根据这次缺图是否有本机副本给出提示。查询失败时，顾客核对内容后可再次点「提交预订」，图片可用时会直接提交。已有独立草稿时可选择「打开另一份草稿」。页面读到另一份草稿后才询问是否切换。确认后若草稿仍可读取，页面会直接打开它。草稿已不存在或切换失败时，页面保留当前填写并提示下一步。顾客原图随已提交填单保留。同一商品的图片选择发生并发冲突时，核对界面并列展示两份参考图片。
